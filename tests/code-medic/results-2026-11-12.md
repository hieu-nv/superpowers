## What this does and does not show

- **No regression** from the sub-skill swap on the six existing scenarios. This is not a skill delta: the baselines
  (2026-11-08) predate the swap and these scenarios do not exercise what changed.
- **Not exercised by any scenario:** that nothing invokes `finishing-a-development-branch` in Phase 3, and that the
  plan carries no `feat:`-style commit step. In all runs the agents made the plan and fix commits during
  implementation, before Phase 4 in the skill's order. Their messages matched the Phase 4 format anyway, but the skill
  does not say when commits happen. A scenario that checks commit timing and message format when a hook runs
  mid-implementation is still missing.
- **Phase 1 read-only** (scenario 1) rests on the agent's own run log: its first state-changing command was
  `git fetch`, then branch creation. Git cannot show this.
- **One rep per cell.** Compliance in 6 of 6 is encouraging, not proof. The plan calls for 5 reps per cell.
- **First dispatch failed.** All six agents were stopped by an API safeguard flagged `reasoning_extraction`. The
  prompt had asked each agent to quote verbatim any reasoning where it weighed deviating from the skill.
  The retry dropped that request, so **no verbatim rationalizations were captured** in this batch.
- **Harness rule that differs from real use:** agents were told to create worktrees with `git worktree add`, not the
  `EnterWorktree` tool, to keep them off the real repository. Several first used a relative path that landed the
  worktree inside the primary checkout and moved it out; that is an `using-git-worktrees` detail, not a
  code-medic rule.
- **Self-reported premise handling:** the scenario 3 agent noted the job text claimed two bugs were already fixed.
  It redid Phases 1 to 3 because the repo had no such changes, as in the 2026-11-08 run.
